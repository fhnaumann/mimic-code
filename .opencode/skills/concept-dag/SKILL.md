# concept-dag

Reading and validating the MIMIC-IV concept DAG stored at
`mimic-iv/concept_dag/concept_dag.json`. Use `mimic_utils concept_dag --check`
to regenerate and verify against the stored artifact.

## Actual schema (from concept_dag.json)

```json
{
  "generator": "concept_dag",
  "parser_version": "sqlglot 30.15.0",
  "source_root": "mimic-iv/concepts",
  "total_concepts": 65,
  "total_edges": 91,
  "nodes": {
    "<stem>": {
      "stem": "<stem>",
      "path": "<category>/<name>.sql",
      "sha256": "<full 64-char hex SHA256>",
      "level": <int>,
      "dependencies": ["<dep_stem>", ...],
      "dependents": ["<consumer_stem>", ...]
    }
  },
  "edges": [
    {"consumer": "<concept>", "dependency": "<dep_concept>"},
    ...
  ],
  "topological_order": ["<stem>", ...],
  "levels": {
    "0": ["<stem>", ...],
    "1": ["<stem>", ...],
    "2": ["<stem>", ...],
    "3": ["<stem>", ...]
  },
  "external_tables": { ... }
}
```

Key facts:
- `nodes` is a **dict** (not an array), keyed by concept stem.
- `sha256` is the **full** 64-character hex string (not truncated).
- `edges` is a list of `{consumer, dependency}` objects.
- `topological_order` is the flat build order.
- `levels` groups stems by build level (0–3).

## Operations (via ConversionController)

### Validate a concept
Run `mimic_utils init <concept>` — this validates DAG membership, derives
the category from the node `path`, and creates PENDING state at
`mimic-iv/concepts_fhir/state/<concept>/state.json`.

### Check dependency readiness
Run `mimic_utils depcheck <concept>`. This uses the controller to verify
all deps are COMPLETED (have a `state.json` with `status: "COMPLETED"`).

### Verify DAG integrity
Run `mimic_utils concept_dag --check`. This regenerates the DAG from source
SQL files and compares against the stored artifact. Exit non-zero on mismatch.

### Full status
Run `mimic_utils status`. Produces a table of all concepts with status,
attempt count, and dependency readiness.

## Build-order constraint

A concept can only be started (`mimic_utils start <concept>`) when ALL
concepts in its `dependencies` list are `COMPLETED` in the controller state.
The controller always enforces this and also enforces concurrency — only one
concept may be in an active state
(RUNNING, VALIDATING_DEMO, or VALIDATING_FULL) at any time.

## External raw tables → candidate FHIR resources

The DAG also documents which `mimiciv_hosp` and `mimiciv_icu` tables each
concept references (under `external_tables`). These are not dependencies —
they're the raw tables that concepts are built on. The following candidates
must be confirmed by the FHIR prober against populated data:

| MIMIC Table (Schema) | FHIR Resource |
|---|---|
| `admissions` (hosp) | `Encounter` |
| `patients` (hosp) | `Patient` |
| `diagnoses_icd` (hosp) | `Condition` |
| `labevents` (hosp) | `Observation` |
| `microbiologyevents` (hosp) | `Observation` |
| `prescriptions` (hosp) | `MedicationRequest` |
| `poe` / `poe_detail` (hosp) | `Procedure` |
| `services` (hosp) | Encounter service |
| `chartevents` (icu) | `Observation` |
| `d_items` (icu) | Metadata |
| `inputevents` (icu) | `MedicationAdministration` |
| `outputevents` (icu) | `Observation` |
| `procedureevents` (icu) | `Procedure` |
| `icustays` (icu) | `Encounter` (ICU stay) |

## DAG regeneration

The DAG is generated by `src/mimic_utils/concept_dag.py` (`concept_dag_generate`).
It parses all concept SQL files, extracts `FROM mimiciv_derived.<concept>`
references via sqlglot, and computes full SHA256s. Run with:
`mimic_utils concept_dag`. Only add concepts or change dependencies by
modifying the canonical SQL; never edit concept_dag.json manually.
