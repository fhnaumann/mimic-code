# Temporary Pathling workarounds applied to exported artifacts

**Status: temporary. Remove once [aehrc/pathling#2730](https://github.com/aehrc/pathling/issues/2730)
and [#2731](https://github.com/aehrc/pathling/issues/2731) are fixed.**

Two exported artifacts carry a hand-applied edit that is **not** produced by
`mimic-utils export-mappings`. Running that command **reverts them**, and they
must be re-applied before the affected concepts are registered on a server. See
[Re-applying](#re-applying) for the two edits and
[Detecting a lapse](#detecting-a-lapse) for how you find out if you forget.

## The bug

A column whose name equals a bound `relatedArtifact.label` is replaced by
Pathling's internal table identifier for that dependency. The server appears to
substitute the label as a *table* reference before resolving names, so a column
that happens to share the label's name gets clobbered.

It has two faces, and only one of them is loud:

| Concept | Collision | Symptom |
| --- | --- | --- |
| `charlson` | reads `src_age.age`; `age`'s Library projects a column `age`, and `age` is also the label bound to `Library/age` | **HTTP 422** `UNRESOLVED_COLUMN`, naming `src_age.sqlquery_…_Library_age_3_…` |
| `bg` | projects a column `specimen`; `specimen` is also the label bound to `ViewDefinition/bg-specimen` | **HTTP 200** — silently serves the column as `sqlquery_…_ViewDefinition_bg_specimen_7_…` |

The `bg` case is the dangerous one: the request succeeds, and only the served
column *name* is wrong, so anything joining on it fails later for reasons that
point nowhere near the cause.

### Evidence

Probed against Pathling `3.0.0-SNAPSHOT`, each a `sql-view` Library depending on
`Library/age`:

| Probe SQL | Label bound to `Library/age` | Result |
| --- | --- | --- |
| `SELECT patient_key, anchor_age FROM age` | `age` | **200** — dependency resolution itself is fine |
| `SELECT patient_key, age FROM age` | `age` | **422** — only the colliding column breaks |
| `SELECT * FROM age` | `age` | **200**, serves `…, age, …` correctly |
| `SELECT patient_key, age FROM age_src` | `age_src` | **200**, `age` = 52 |

The third row shows the materialised dependency really does have a correctly
named `age` column, so the port's SQL is valid and this is not a mapping error.
The fourth row is the workaround.

## The workaround

**Rename the label, not the column.** Both sides of the collision are ours to
rename, but the columns are the artifact's public interface — the thing
downstream code selects — while a label is an internal table alias, private to
one Library. Renaming labels means no concept's served columns change, and each
edit stays inside the one broken artifact instead of rippling into every consumer
of `age`.

Concretely, renaming `age`'s column would have changed `age`'s schema *and*
forced a matching edit in `charlson`; renaming `charlson`'s label touches only
`charlson`.

## Re-applying

Each edit is a label rename plus the single matching table reference in the SQL.
The SQL lives in **three** places that `export-mappings` asserts agree, so all
three must move together: `content[0].extension[0].valueString` (the `sql-text`
extension), `content[0].data` (base64 of the same bytes), and the
`<concept>.sql` readability sidecar.

### `measurement/bg`

- `Library.bg.json`: `relatedArtifact[].label` `specimen` → `specimen_src`
  (leave `resource` pointing at `…/ViewDefinition/bg-specimen`)
- SQL: `INNER JOIN specimen s` → `INNER JOIN specimen_src s` (one occurrence)
- Leaves the projected column `specimen` untouched — that is the point

### `comorbidity/charlson`

- `Library.charlson.json`: `relatedArtifact[].label` `age` → `age_src`
  (leave `resource` pointing at `…/Library/age`)
- SQL: `FROM age AS src_age` → `FROM age_src AS src_age` (one occurrence)
- Leaves the `src_age.age` references untouched

Do **not** rename the ViewDefinition/Library `id` or `url`: the label is only a
table name, and the canonical is what binds it to a resource.

`Library.version` is deliberately **not** bumped. It carries the attempt number,
so bumping it would misstate which attempt these bytes came from.

Note that the sidecar banner still claims the file was generated by
`metrics-finalize`. For these two files that is now false, and it will become
true again the moment the workaround is dropped.

## Detecting a lapse

You do not have to remember. `register-derived-concepts` smoke-tests every
concept and compares the served column names against the Library's SQL
projection, so both faces of the bug surface at upload time:

- `charlson` reverted → `smoke FAILED (HTTP 422)` with the `UNRESOLVED_COLUMN` text
- `bg` reverted → `smoke FAILED (HTTP 200)` with a `served columns differ` diff

Both are warnings, not failures: the command still exits `0` and the resources
are still registered. That is deliberate (registering a view and executing one
are different things), but it does mean **the exit code will not tell you** — read
the summary line.

## Removing this

When #2730 and #2731 land:

1. Re-run `mimic-utils export-mappings` to restore the generated artifacts.
2. Re-run `mimic-utils register-derived-concepts --all` and confirm every concept
   smokes clean with no relabelling in place.
3. Delete this file and the cross-reference in `src/mimic_utils/artifact_upload.py`.

Until then, any newly ported concept that projects a column sharing a name with
one of its `relatedArtifact` labels will hit the same bug. The collision is
mechanically checkable: compare each Library's outermost projection against its
set of labels.
