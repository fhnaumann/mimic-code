# ViewDefinition deduplication — working doc

> Temporary working document. Delete once the work lands or is abandoned.
> Scope: `artifacts-curated/` only. `artifacts/` is regenerated by script and must not be hand-edited.

## Why this exists

The concept mappings were produced by agents running in parallel, one concept per agent.
Each agent emitted its own ViewDefinitions, so there is no shared ViewDef layer beneath
the SQL. SQL-on-FHIR's premise is the opposite: a small set of reusable ViewDefinitions
with concept SQL layered on top. This doc records whether closing that gap is worth it,
and the plan for doing so.

## Survey of the current state

186 ViewDefinitions across 64 concepts, 68 distinct dependency labels.

**No ViewDefinition contains a `where` clause.** All 186 are pure projections; every
filter lives either in the SQL or inside a `forEach` expression.

113 of 186 files are structurally identical to at least one other file (comparing
`resource` + `select` + `where` + `constant`, ignoring naming metadata). Byte-level
they are all distinct, because `name`/`id`/`url` are per-concept.

### Two regimes

The corpus splits cleanly by what `forEach` is applied to:

| Regime | Resources | Count | `forEach` target | Dedupable |
|---|---|---|---|---|
| **Spine** | Patient, Encounter, Specimen, Condition, Medication, MedicationRequest | ~148 | `identifier.where(system=…)` — concept-independent | Yes, heavily |
| **Payload** | Observation, MedicationAdministration, Procedure | ~38 | `code.coding.where(… code='220045' …)` — the concept's item list | No, by design |

Payload views bake each concept's itemid set into the `forEach`. That is a projection
pushdown, not accidental duplication — merging them would force a full chartevents /
labevents scan per concept. **They stay as they are.**

Duplication counts per spine resource:

- Patient — 43 views, 39 of them identical modulo `name`
- Encounter — 78 views, 33 distinct column-sets
- Specimen — 9 views, 7 identical
- Condition — 4 views, all identical `forEach`
- Medication family — 18 views, 4 distinct shapes

Realistic collapse: ~148 spine views → roughly 12. Corpus 186 → ~40.

### Why the refactor is cheap

`Library.relatedArtifact[]` maps a **label** (the table name the SQL uses — `patient`,
`icu_encounter`) to a **resource URL**. The SQL never names a ViewDefinition globally.
Deduplication is therefore a rebinding: point `resource` at a canonical URL, keep the
`label` unchanged, and the SQL needs no edit — provided column names and row cardinality
match. Those two provisos are what steps 1 and 2 exist to establish.

Note: each `Library.*.json` carries its SQL in three synchronised places —
the `sql-text` extension `valueString`, the base64 `content.data`, and the sibling
readability `.sql` file. Any SQL edit must update all three.

## Blockers found

Three inconsistencies that a naive merge would silently propagate. These are worth
fixing on their own merits, independently of whether the dedup proceeds.

### 1. `encounter_key` is overloaded (safety-critical)

`encounter_key` means `getResourceKey()` in 44 views and
`partOf.getReferenceKey(Encounter)` — the *parent hospital* encounter — in 7 views.
Same name, two different grains. Joining on it across concepts silently yields wrong
results.

Widening the search to the underlying path rather than the name: **13 views project
`partOf.getReferenceKey(Encounter)` under three different names**:

| Name used | Views |
|---|---|
| `encounter_key` | 7 — first_day_sofa, meld, apsiii, lods, oasis, sapsii, sirs |
| `parent_encounter_key` | 5 — icustay_detail, icustay_times, kdigo_creatinine, kdigo_stages, sofa |
| `hospital_encounter_key` | 1 — antibiotic |

All 13 base resources are ICU encounters (each also projects `stay_id_str` from the
`encounter-icu` identifier system), so the parent is always the hospital encounter.
`hospital_encounter_key` is both accurate and already precedented.

Seven of these views project `icu_encounter_key` = self *and* `encounter_key` = partOf
side by side — within one view, `encounter_key` does not mean self.

### 2. The self key has two names

`getResourceKey()` on an Encounter is named `encounter_key` in 44 views and
`icu_encounter_key` in 34. Same path, two names, and the SQL references them by name.
Unifying requires either touching the SQL or emitting both aliases.

*Deferred to step 2*, where the canonical views are defined — doing it now would mean
renaming twice.

### 3. `forEach` vs inline path is a semantic difference

54 Encounter views extract the identifier via `forEach`; 24 use an inline
`identifier.where(…).value` column. Per the SQL-on-FHIR spec `forEach` drops rows whose
collection is empty, while the inline column keeps the row with a null. Same nominal
view, different row counts.

Migration is tractable because the SQL already defends against this: of 64 SQL files,
**40 filter `<id> IS NOT NULL`** and **37 re-filter the identifier system**. Unify on
`forEachOrNull` and those 40 absorb the change with no diff; the remaining ~24 need
checking individually.

### Dead code (consequence of 3)

Views that `forEach` on the ICU identifier also project `stay_system`, and their SQL then
does `WHERE stay_system = '…encounter-icu' AND stay_id_str IS NOT NULL`. Both predicates
are provably always true given the `forEach`. 37 of 64 SQL files carry the redundant
system filter, 40 the redundant null check.

## Plan

1. **Normalize column naming.** Eliminate the `encounter_key` overload: every projection
   of `partOf.getReferenceKey(Encounter)` becomes `hospital_encounter_key`. Retires
   `parent_encounter_key`. After this, `encounter_key` always means "this view's own
   encounter". Own commit; valuable even if the rest is abandoned.
2. **Define ~12 canonical spine views** — `patient`, `icu_encounter`, `hospital_encounter`,
   `specimen`, `condition`, `medication`, `medication_mix`, `medication_request`, plus a
   few variants. Superset columns, `forEachOrNull` throughout. Unify the self-key naming
   (blocker 2) here.
3. **Rebind** `relatedArtifact.resource` per Library, keeping labels. Payload views
   untouched.
4. **Verify** by re-running each concept and diffing against current outputs.
   `oracle/oracle_manifest.full.json` and the per-concept `metrics/` directories provide
   the equivalence harness, so this is mechanically checkable.

Steps 1 and 4 are the non-negotiable ones; step 3 is only safe because of step 4.

The writeup should be honest that payload views stay concept-specific by design. The
claim is not "we deduplicated everything" — it is "the join spine is shared, and the
item-code projections are per-concept because that is where the filtering pushdown lives."

## Step 1 — execution log

**Convention adopted:** `hospital_encounter_key` = `partOf.getReferenceKey(Encounter)`,
everywhere. `parent_encounter_key` retired. `encounter_key` left meaning self (its
grain naming is step 2's problem).

**Care required:** renaming a ViewDefinition column requires updating every SQL reference
to it. A blind find/replace is unsafe because `encounter_key` is also a legitimate column
on *other* views joined in the same query, and may appear in a concept's final SELECT —
where it forms part of the concept's output contract and must not be renamed.

**Status: done.** 12 concepts changed, 36 files (12 ViewDefinitions, 12 `.sql`, 12
`Library.*.json`). `medication/antibiotic` already used the target name and was left alone.

### What changed

Two groups, handled differently:

*Whole-file replace* — old name `parent_encounter_key`, which was unique within its
concept and never an output column:
`demographics/icustay_detail`, `demographics/icustay_times`,
`organfailure/kdigo_creatinine`, `organfailure/kdigo_stages`, `score/sofa`.

*Targeted rewrite* — old name `encounter_key`, which collided with the hospital view's
own key and reached the final SELECT. Only the direct read of the ICU encounter view was
rewritten; where a CTE re-exported the column the reference was aliased back
(`i.hospital_encounter_key AS encounter_key`), so **every concept's output columns are
unchanged**: `firstday/first_day_sofa`, `organfailure/meld`, `score/apsiii`, `score/lods`,
`score/oasis`, `score/sapsii`, `score/sirs`.

Readability improved where the convention now lines up, e.g. `icustay_detail`:

```sql
-- before:  ON i.parent_encounter_key = h.hospital_encounter_key
-- after:   ON i.hospital_encounter_key = h.hospital_encounter_key
```

Both sides now name the same referent. On a hospital-encounter view
`hospital_encounter_key` is its own key; on an ICU view it is the parent. Same meaning,
one name.

### Invariants verified after the change

| Invariant | Result |
|---|---|
| Names used for `partOf.getReferenceKey(Encounter)` | `hospital_encounter_key` only, 13 views |
| Paths behind `encounter_key` | `getResourceKey()` only, 44 views — **overload gone** |
| Paths behind `hospital_encounter_key` | `partOf.getReferenceKey(Encounter)` only, 13 views |
| `parent_encounter_key` anywhere in the tree | 0 files |

### Tooling added

Both scripts live at the repo root and are reusable for steps 2–3.

- **`sync_library_sql.py`** — regenerates `Library.*.json` `sql-text` + base64 `data`
  from the sibling `.sql` body. `--check` (default) verifies all three copies agree;
  `--write` regenerates. Validated by round-tripping all 64 concepts with zero diffs
  before any edit, so the header-splitting is known-correct. JSON formatting is stable
  (`json.dumps(indent=2)` reproduces every Library and ViewDefinition byte-for-byte),
  so diffs stay surgical.
- **`verify_view_columns.py`** — resolves each `relatedArtifact` label to its
  ViewDefinition's column set, parses the SQL with sqlglot, and checks every
  alias-qualified reference to a base view against that set. Currently **1094 column
  references across all 64 concepts, 0 unresolved**. Negative control passed: renaming a
  column in one ViewDefinition without touching its SQL is reported as `UNRESOLVED`.

This is the static half of step 4's verification. It proves the SQL and the
ViewDefinitions agree on column names; it does **not** prove row counts are unchanged.
That still needs an execution diff against `oracle/` — and it is what will actually
validate the `forEach` → `forEachOrNull` change in step 2.

## Step 2a — execution log (self-key naming, blocker 2)

**Done.** The convention is now total across all 78 Encounter ViewDefinitions:

| Name | Meaning | Views |
|---|---|---|
| `encounter_key` | a hospital encounter's own `getResourceKey()` | 28 |
| `icu_encounter_key` | an ICU encounter's own `getResourceKey()` | 50 |
| `hospital_encounter_key` | the hospital encounter, from either grain (`partOf`) | 13 |

Each name now resolves to exactly one path. Before step 1 the first two overlapped and
`partOf` went under three different names.

27 hospital views and 34 ICU views already followed this; **16 ICU views named their self
key `encounter_key`** and were changed. Their SQL had been aliasing it back to
`icu_encounter_key` for the output anyway — which `oracle_manifest.full.json` expects —
so the rename *removed* an alias and **changed no concept's output columns**.

`score/oasis/ViewDefinition.hospital_service.json` projects `serviceType.coding` (MIMIC's
`services` table, hospital grain) and correctly keeps `encounter_key`.

Process note: the first pass fixed one reference site per concept and
`verify_view_columns.py` then flagged **11 missed join predicates** (`ON x.encounter_key =
e.encounter_key`) that the initial grep had not matched. Those were fixed in a second
pass. The static verifier earned its keep here — that class of miss would otherwise have
surfaced only at execution time.

Final state: 1094 column references across 64 concepts resolve, 0 problems; all 64
Libraries agree with their `.sql`.

## Findings that change steps 2b and 3

Two things surfaced while checking whether shared views are loadable at all. Both are
decision points for the author, and both mean **step 3 as originally written is not
achievable by editing artifacts alone**.

### The per-concept ViewDefinition layout is the export format's design

`src/mimic_utils/export_mappings.py` does not read a canonical URL off a shared view — it
*derives* one per concept:

```python
bindings[label] = f"{VIEWDEFINITION_BASE}/{concept}-{label}"
```

It discovers views by globbing the concept's own attempt directory, and raises
`StateError` for any table that is neither a shipped ViewDefinition nor a declared
dependency. `artifact_upload.py` likewise requires every concept bundle to ship its own
views. The module docstring states the intent outright: labels are *"scoped to this
Library, which is why per-concept ViewDefinitions can share a `name` without shadowing
each other."*

So the duplication measured at the top of this document is **not an artefact of running
the mappings in parallel**. It is what the publication format asks for: each concept is a
self-contained, independently registerable bundle. Rebinding to shared canonical URLs
would require changing `export_mappings.py` (URL derivation *and* view discovery) and
`artifact_upload.py` — i.e. changing the publication contract, not the artifacts.

This also reframes the original question. "SQL-on-FHIR wants shared reusable ViewDefs" is
true of the *spec*, but this pipeline deliberately trades that for bundle self-containment.
That is a defensible choice and worth stating explicitly in the writeup rather than
presenting the duplication as a defect.

### `artifacts-curated/` is downstream of `concepts/*/attempt_*/`

The `.sql` header says it: *"generated by `mimic-utils metrics-finalize` from the finalized
attempt."* The real source is `concepts/<domain>/<concept>/attempt_NNNN/`, which feeds both
`artifacts/` (186 ViewDefinitions, script-overwritten) and `artifacts-curated/` (186, edited
here).

The attempt directories still carry the old names — e.g.
`concepts/score/apsiii/attempt_0002/ViewDefinition.icu_encounter.json` still has
`encounter_key = partOf.getReferenceKey(Encounter)`. **`artifacts-curated/` has therefore
diverged from its source, and a re-export would revert steps 1 and 2a.**

### Resolution

Both findings are moot for this project. The agentic pipeline existed to *produce* the
artifacts; `artifacts-curated/` is now the hand-maintained source of truth, refined
directly. The work does not need to be reproducible from the attempt directories, only
traceable, and the goal is a publishable set of artifacts. So the exporter is not re-run,
and shared canonical URLs are free to use. Steps 2b and 3 proceeded on that basis.

### Options considered (superseded by the above)

1. **Propagate steps 1+2a upstream** into the attempt directories so a re-export
   reproduces them, then stop. Keeps the naming fix — the part with real safety value —
   and abandons structural dedup.
2. **Change the exporter** to support shared views, then do 2b/3 properly. The largest
   option, and the only one that delivers a genuine shared ViewDef layer.
3. **Treat `artifacts-curated/` as a hand-maintained deliverable** that intentionally
   diverges from the generated `artifacts/`, and document the divergence.
4. **Normalize `forEach` → `forEachOrNull` per-concept** (blocker 3) without sharing.
   Improves consistency and removes the dead `IS NOT NULL` / system filters, needs no
   exporter change — but does change row semantics, so it requires an execution diff
   against `oracle/`.

| Encounter | 78 | **5** |
| Specimen | 9 | **2** |
| Medication | 10 | **4** |
| MedicationRequest | 4 | **2** |

| MedicationAdministration | 9 | 9 (unchanged) |

30 of the 64 concepts now ship **no** ViewDefinitions of their own — they are served
entirely by `_shared/`. No dangling references; no orphaned shared view.

### The safety rule that made this mechanical

Two views may be merged only if they iterate the *same collections*. The grouping key is
`resource` plus the **exact set of `forEach` contexts**, which keeps three dangerous cases
apart automatically:

- `forEach` on an identifier **drops** resources lacking it; an inline
  `identifier.where(...).value` column **keeps** them with a null. Different row counts —
  never merged.
- Two views with *different* `forEach` expressions would **cross-join** if combined.
- `forEachOrNull` is distinct from both.

So `icu_encounter` (38 consumers, `forEach` on the ICU identifier — ICU stays only) and
`encounter` (24 consumers, no `forEach` — every Encounter, identifier columns null where
the grain does not apply) remain separate views. This is why blocker 3 was *not* resolved
by converting everything to `forEachOrNull`: that would have changed row counts in a way
nothing here can verify. Recognising the two as distinct, legitimate view flavours is both
safer and a more honest description of what they are.

Checked before committing to that: 10/12 ICU-inline and 11/12 hospital-inline consumers
already filter `IS NOT NULL`, and `sepsis3` is protected by an `INNER JOIN` — but
`suspicion_of_infection` genuinely differs, which settled it.

The `encounter` view is worth noting: because it has no `forEach` at all, one view with 11
columns serves both grains — `hadm_id_str` is null on an ICU stay, `stay_id_str` on a
hospital admission — with no filtering and no row multiplication.

### Naming normalisation this required

Merging exposed alias-duplicates — one path under several names — which would have made
the shared views absurd (`intime`, `intime_datetime` and `period_start` all mapping to
`period.start`). 24 further column renames were applied across 17 concepts:

- ICU encounters: `intime_datetime`, `outtime_datetime`, `stay_system`
- Hospital encounters: `hadm_system`, `patient_key`
- Patient: `gender` (was also `gender_fhir`)
- Condition: `code`, `system` (were also `icd_code`/`diagnosis_code`,
  `code_system`/`diagnosis_system`)
- Specimen: `patient_key`, `collection_datetime`

Several views also declared columns **no SQL ever read** — `meld` alone had four. The
merge dropped them.

Two Patient views extracted `subject_id_str` via `forEach` rather than an inline path.
They were converted to inline so all 43 could share one view. This is the single place
where an assumption was made rather than proved: **every MIMIC Patient carries exactly one
identifier with the MIMIC patient system** — which is how `subject_id` is represented, so
it holds by construction. Column names were unchanged, so no SQL was affected.

### Verification

After every stage: **1094 column references across 64 concepts resolve, 0 problems**, and
all 64 Libraries agree with their `.sql`. The rebind additionally refuses to act unless
the shared view's columns are a superset of the per-concept view's *and* the two agree on
`forEach` signature — a rebind that would change a column or a row count fails loudly
rather than silently.

**This is still static verification.** It proves the artifacts are internally consistent —
names resolve, cardinality is preserved by construction. It does not execute anything. The
one claim resting on domain knowledge rather than proof is the Patient identifier
assumption above.

### Tooling

- **`rebind_shared.py`** — repoints Libraries at `_shared/` and deletes the superseded
  per-concept file. `--write` to act; dry-run by default. Each concept keeps its own
  `relatedArtifact.label`, so **no concept SQL changed during the rebind** — labels are
  Library-scoped, which is what lets `icu_encounter`, `encounter_icu` and
  `rrt_encounter` all bind to the same shared view.
- `verify_view_columns.py` now resolves shared views as well as per-concept ones.

### Caveat on review

Only 3 of the 12 changed concepts are tracked in git — `icustay_detail`,
`icustay_times`, `kdigo_creatinine`. The other 9 (`first_day_sofa`, `kdigo_stages`,
`meld`, `apsiii`, `lods`, `oasis`, `sapsii`, `sirs`, `sofa`) are untracked, so `git diff`
will not show those edits. The working tree also carried unrelated pre-existing
modifications before this work started, so the diff is not attributable to step 1 alone.
